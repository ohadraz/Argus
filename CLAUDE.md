# Argus - Project Context for Claude

## What this is
Argus is an autonomous incident-response agent (course project). Full spec:
`docs/spec-and-architecture.md`.
It is a **multi-agent system**, not a single chatbot: an orchestrator delegates to specialized parts (the Investigator and Code-Fix agents, the Mitigator, the Communicator and the Postmortem Writer) that investigate alerts, take reversible mitigation actions, propose code fixes via PR, and write postmortems - against a self-contained **Target Service + Target Environment** it builds and controls (spec §2, §15), not real infra or a `modules/sandbox/` package.

## Repo structure - this is a uv workspace (Python's multi-module repo)

- `pyproject.toml` (root) - workspace definition only, not an installable package
  (`[tool.uv] package = false`). Declares `[tool.uv.workspace] members = ["modules/*", "test_support/*"]` and the shared `[dependency-groups] dev = [...]` (pytest, ruff, mypy, nox, pre-commit).
- `modules/<name>/` - each is an **independent package**: own `pyproject.toml`, own version, own `src/<package_name>/`, own `tests/`. One shared `uv.lock` resolves third-party deps workspace-wide; each module's own version is independent and never auto-bumped by uv.
- `modules/core/` - shared library (schemas, LLM client, logging, config; config here is Argus's own settings, and `AdapterSettings`, the base each vendor's adapter declares its own settings on - under the variable names a deployment always set). Other modules depend on it via `{ workspace = true }` in their `pyproject.toml`.
- `modules/apps/` - each process's composition root and nothing else: `python -m apps.<process>` for `worker`, `web`, `read_mcp`, `write_mcp`, `deliverer`, `indexer`, `relay`, `intent_reader` and `schema`. A root builds every vendor's adapter its process uses and hands each library its port, and starts the process's telemetry (every process's but the schema job's); nothing else imports an adapter, the telemetry SDK or a root, and no root reaches another. One extra per process (`argus-apps[web]`, `[worker]`, ...), so installing a process installs what it runs - the web process still installs no agent.
- `modules/incident_record/` - the incident record: the tables, their repositories, and the operations on an incident that are not the walk (intake, a person's ending - one path, `AtAPersonsWord`, whichever door they said it through - and event publishing), and the decisions a door asks before an ending (`incidents_a_page_is_about`, `the_incident_of_thread`, `accept_offer`). What it holds is reached by role, never by table: `IncidentReads` (one incident), `IncidentsOnShow`, `IncidentNames`, `IncidentConversation`, `TheWalksWrites`, `RunQueue` and `RatesCache`, each built on a connection its caller holds (`<role>_on(conn)`, so a write commits with the line published beside it, and several reads are one moment inside `postgres.at_one_moment`) and, where a caller holds only `Connections`, over those (`<role>_over(connections)`, which opens nothing until asked). `incident_record.repository` is the package's own - a `protected` contract refuses it to everything that ships outside the package; a suite arranging rows still reaches it. Depends on `core` and `postgres` alone, which is what lets `web_app` serve HTML without installing LangGraph or any agent.
- `modules/narration/` - the event-to-sentence renderer: an incident's recorded events said in words, one line per event, for every destination that has to say what happened. It lives outside the page because the dashboard, Slack and the postmortem all tell the same story and must tell it in the same words. It also holds how a day, a time, a level, a span, an amount of money and a revision are said (`said_as_a_day`, `said_as_a_level`, `said_as_a_span`, `said_as_money`, `short_form` and their kin), and the lesson on detection as one sentence, for the same reason. Takes values and returns values - no database, no markup; whoever is doing the showing decides what to wrap around a line.
- `modules/incident_cost/` - what an incident cost in money, apart from the agent that writes it up: the money ports (revenue, exchange rates, pay bands, with the working year and the reporting currency, as `MoneySources`), their read and their arithmetic - the loss estimate (`estimate_loss`), the response's price (`responder_cost`) and how it was arrived at (`response_cost_basis`). Depends on nothing in this workspace, so costing is read and tested without the Postmortem Writer.
- `modules/postmortem_rendering/` - the postmortem as a reader reads it: every word of it worked out once, as lines of pieces each marked with the part it plays, for the page and for the PDF (`as_pdf`, fpdf2, its fonts shipped as package data) to wrap in their own look. Takes values and returns values, like `narration`, and depends on `core` and `narration` alone - which is what lets `web_app` serve both forms without installing the agent that wrote the document.
- `modules/executive_synopsis/` - the executive synopsis: the incident in one paragraph for the people who lead, written from the stored postmortem and never changing it. It prices the response itself, from the postmortem's minutes by title, through `incident_cost`. It depends on `postmortem_writing` for its figure engine and its judge, and the writer never on it - a contract of its own holds that.
- `modules/repository_index/` - the index of the Target Service's source, searched by meaning (spec §11.5): what a repository is cut into, how a passage becomes a vector, where the vectors live, and the catch-up loop that keeps the two commits - the one the passages describe and the one the repository is at - from differing. Each recipe the index is built with (`recipe.built_with`: the embedding model, the chunk bounds and the service's directories) is a collection of its own, named by `core.embedding.collection_for`, with a mark of its own. It speaks the kernel's vector-store ports (`core.vector_store`) and its `Embedder` port (`core.embedding`), never the vendor; it installs neither the store's client nor the embedding model, which is what lets `web_app` write the watermark row without installing an ONNX runtime to serve a page. The embedder is built by `embedding_fastembed` in the roots that embed, and the store adapter's writing side is built by the catch-up loop's root, `apps.indexer` (the read server's root, `apps.read_mcp`, builds its reading side for search by meaning).
- `modules/incident_memory/` - what earlier incidents were done about, kept for the ones that come after (spec §11.2). A cause is re-derivable from the incident in front of you; what was *tried* and what each attempt reached is not, and exists only in the record of the incident that tried it. So this holds the record, the text it is found by, the row it is filed in, the Qdrant collection it lives in (one per embedding model, each with its own delivery marks), and the one thing it is allowed to change: the order a later walk tries its candidates in. The walk *files* the record (`filing`, a row the fence refuses for a lost run) and *recalls* (`recalling`); it never writes the store. The deliverer (`delivering`, run by its root `apps.deliverer`) carries filed rows into the store through `keeping`, one deliverer at a time under an advisory lock. `keeping` and `recalling` are handed the store as the kernel's ports (`VectorIndex`, `VectorSearch`), with the collection already chosen, and the embedder as `core.embedding.Embedder`. The package installs neither the store's client nor the model: the two processes that search or keep - the worker, whose root builds recall, and the deliverer - build both adapters in their roots. Depends on `core` alone - the store's adapter, the embedding model and the telemetry SDK are the roots', and the actions are handed to it, the way `narration` is handed events.
- `modules/embedding_fastembed/` - the embedding model's adapter: `an_embedder(model_name)`, a fastembed model run in-process behind the kernel's `Embedder` port (`core.embedding`), loaded on first use. Built only by the roots that embed - the worker's (recall), the deliverer's (keeping), the index's and the read server's - and handed on as the port - the composition-root contract holds that only roots may, and the guard's extras check which.
- `modules/llm_anthropic/` - the model provider's adapter: `AnthropicProvider` and `AnthropicSettings` behind the kernel's `ModelProvider` port (`core.llm`), with its translations (`to_tool`, `to_turn`, `to_messages`) and wire vocabulary (the stop reasons and block types), which its suites and the files standing in for a root name from it. The one package that installs the Anthropic SDK; built only by the worker's and the Intent Reader's roots and handed to every agent as the port - the composition-root contract holds that only roots may, and the guard's extras check which.
- `modules/vector_store_qdrant/` - the vector store's adapter, and the only shipped code that imports `qdrant_client` (spec §12) - two scripts under `scripts/` import it too (one measures where scores land, one records an incident), and ship nothing. The ports it answers are the kernel's, `core.vector_store`, split by side: `VectorSearch` (nearest points, narrowed by `Equals`/`StartsWithAnyOf` conditions and a floor, all applied by the store while it ranks) and `VectorIndex` (that, plus `ensure`, `upsert`, `delete` and `held`). The adapter is split the same way: `searching` (`QdrantSearch`, `SearchOpenedOnFirstUse`, `the_search_at`) is what the worker's root and the read server's root build; `indexing` (`QdrantIndex`, `the_index_at`) is what the deliverer's and the index's roots build, and nothing else may - the walk's contract forbids it the worker's root, and a contract of its own leaves it to those two roots. `settings` (`QdrantSettings`) is what each root reads the store's address from. `ensure` re-indexes a field in place when its index cannot serve a prefix asked of it, so an existing collection needs no drop - but only on a write, and the index's catch-up loop writes only when a file changes: until then an older collection answers its scope by a scan, slower and never wrong. Each process's root, in `apps`, is the only place it is built - a layering contract and the guard hold that.
- `modules/postgres/` - Argus's own database: where a connection comes from (`Connections`, `open_pool`, `unit_of_work`, `connect`, and `connect_from_env` for suites and scripts), saying on one which run it writes for (`fence`, and the pool that fences every connection it hands out), the schema one job applies and every service refuses to start without (`reset_schema`; `open_pool` refuses a database with no schema, and `require_schema_at` asks for a process that holds no pool), and the Alembic chain (`postgres/migrations/`). A package of its own so the kernel installs no driver; the kernel keeps what a claim is and how a lost run is known (`Fence`, `Holding`, `RunLost`, `was_lost`).
- `modules/mcp_transport/` - how Argus reaches an MCP server and answers as one: `McpClient`, the session held to each server and rebuilt once when its transport drops; `TracedMCPServer`, the server that answers inside its caller's trace and answers a refusal with the refusal whole; and the refusal itself (`ToolRefusal`, its `ToolRefusalKind`, and `ToolRefused`, what a write tool raises), with the functions that build one (`an_exhausted_action`, `a_change_made_since` and their kin). A package of its own so the kernel installs no MCP SDK, HTTP client or ASGI server; the two tiers' clients, both servers, the Mitigator and the walk take it.
- `modules/http_applying/` - whether a failed HTTP request is known not to have been applied (`known_not_applied`), the one rule the deployment platform's and the flag provider's write paths share. A package of its own so the kernel installs no HTTP client; it depends on nothing in this workspace.
- `modules/deployment_platform/` - the deployment platform as Argus needs it: a port named for the role, split by tier (`DeploymentPlatformReads` for the read server, `DeploymentPlatformWrites` for the write server), returning Argus's own values (each deployment marked `made_by_argus` by the adapter), and one adapter named for the vendor (`deployment_platform.argocd.ArgoCd`). Only the adapter knows a route, a selector or a response body, and only each server's root (`apps.read_mcp`, `apps.write_mcp`) may build it - the composition-root contract holds that only roots may, and the guard's extras check that only those two do.
- `modules/alerting_platform/` - the platform that evaluates the rules that page, for the read server: `AlertingPlatform` (a rule's `RuleEvaluation` - where it stands, its durations, the series it watches and the unit the platform shows it in - and the series alone, for the metrics read) and one adapter, `alerting_platform.grafana.Grafana`. The rule's query travels as an opaque `SeriesQuery` (`core.models`, beside `RuleSeries`); only `metrics_source`'s Prometheus adapter reads one (`what_the_series_is`: what it measures, and the unit its metric's name carries), and `read_mcp_server.alert_rules` composes the two answers into `AlertRuleStanding`. Units are the kernel's `Unit`, and each adapter translates its vendor's ids into it. Only the read server's root (`apps.read_mcp`) may build either adapter - the composition-root contract holds that only roots may, and the guard's extras check that only that one does.
- `modules/alert_source/` and `modules/push_source/` - the inbound senders, for the web application: `AlertSource` (a delivery's bytes and headers read as an `Alert` or `OnlyResolved`; one adapter per sender, `alert_source.grafana` the first, each on its own route `/webhooks/alerts/<sender>`, with the bare `/webhooks/alerts` the first sender's) and `PushSource` (a verified delivery read as a `Pushed` - repository, ref, commit; adapter `push_source.github`, which refuses everything where no secret is set). Both know only the kernel, and only the web process's root (`apps.web`) builds their adapters and hands them to `web_app.app.an_app`.
- `modules/flag_provider/` - the feature-flag provider, built the same way: `FlagProviderReads` for the read server, `FlagProviderWrites` (which includes `FlagAudit`, the change log with each change marked `made_by_argus`) for the write server, and one adapter, `flag_provider.unleash`, whose settings are its own (`UNLEASH_*`, on the kernel's `AdapterSettings`). Only the adapter knows a route, a token kind or an event name, and only each server's root (`apps.read_mcp`, `apps.write_mcp`) may build it.
- `modules/code_host/` - the code host, built the same way: `CodeHostReads` (a repository's files, one file, its whole source at a commit, what changed between two commits, where a branch points, whether it contains a commit, where a deployed revision is read) for the read server and the index, `CodeHostWrites` (a fix committed to a branch of its own, proposed as a draft - safe to ask again, and with no merge; no reads) for the write server, and one adapter, `code_host.github`: `GitHubReads` holding the read token alone, `GitHub` holding the token that pushes alone. Only the adapter knows a route, a media type, an archive's layout or a field of GitHub's answer, and only the servers' roots (`apps.read_mcp`, `apps.write_mcp`) and the index's (`apps.indexer`) may build it.
- **MCP servers are split by autonomy tier, not per integration** (spec §12.1): one read-only server and one write server, each paired with a typed client package (`*_mcp_server` / `*_mcp_client`). The server is a library its tier's process serves - built and served by its root (`apps.read_mcp`, `apps.write_mcp`); the client is a library installed into calling agents, exposing each tool as a typed method of its tier's class (`ReadTier`, `WriteTier`, which share no type, so one tier handed where the other is named fails mypy) rather than a stringly-typed `call_tool(name, **kwargs)`. Shared transport lives once in `mcp_transport`.
- `tests/` (repo root, outside `modules/`) - cross-module tests only:
  - `tests/integration/` - multiple modules interacting in-process, against a real postgres its own `conftest.py` brings up and empties between tests, and the Anthropic double, GitHub double and write MCP server `nox -s integration` starts on ports of its own
  - `tests/e2e/` - full stack via docker-compose, real chaos scenarios end-to-end
  - `tests/contract/` - verifies a test double still matches the external party it stands in for, one subdirectory per party: `anthropic/` (`anthropic_double` against the real Anthropic API, run by `nox -s paid_contract`, which spends tokens), `slack/` (`slack_double` against a real workspace), `stripe/` (the Target Service's `/stripe` stand-in against a Stripe sandbox, whose key is `STRIPE_API_KEY` - it takes a charge there), `frankfurter/` (the Target Service's `/frankfurter` stand-in against the public, keyless Frankfurter) and `prometheus/` (the Target Service's `/prometheus` stand-in against a real Prometheus scraping it, with a wait of up to a minute and a half for Prometheus to watch a minute end). All but the first are free, run together by `nox -s contract`, and so run in the nightly
- `noxfile.py` - cross-module task runner. Sessions: `lint`, `typecheck`, `test_module` (parametrized per module, auto-discovered: every member of `modules/` or `test_support/` that has a `tests/` directory), `test_all`, `integration`, `contract`, `paid_contract`, `eval`, `e2e`. Run `uv run python -m nox --list` to see current sessions.
- `test_support/` - workspace members that the suites run on and nothing ships: the testkit and the doubles. **All of it is off-limits to Claude**, enforced by the hook on the directory rather than a list of names - propose changes in chat. None has a suite of its own: a double of a vendor is held by its contract test against the party it stands in for (`tests/contract/`), and a double of Argus's own port by that port's suite, which runs it beside the vendor's adapter; a gap is closed there, not by testing the double.
  - `test_support/argus_testkit/` - shared test support (`Scenario`, `Assertion`, `all_of`, `eventually`), consumed as a **dev dependency** (`[dependency-groups] dev` + `[tool.uv.sources] ... { workspace = true }`), never a runtime one.
  - `test_support/anthropic_double/` - a record/replay stand-in for the Anthropic API (`POST /v1/messages` plus a `/double-control/*` seam), so the integration and contract suites exercise the real adapter with no key and no spend. No `core` dependency. It is the evidence the adapter is judged against.
  - `test_support/slack_double/` - a stand-in for Slack's `chat.postMessage` plus a `/double-control/*` seam, so the relay's own suite and the e2e stack post with no workspace and no token.
  - `test_support/github_double/` - a stand-in for the GitHub API Argus reads and proposes fixes through, holding a snapshot of the Target Service as its one branch, plus a `/double-control/*` seam that stages commits. Every suite's stack proposes to it; `e2e`, `record` and `stack` reach the real repository.
  - `test_support/target_service_double/` - the shop served through a stand-in that moves its draws to a recording's minutes, so a replayed answer citing a figure finds the one it was recorded citing. Run by `e2e_replay` and `record` only, inside the shop's own container (`docker-compose.replay.yml`).
  - `test_support/pagerduty_double/` - a stand-in for the five PagerDuty reads Argus makes (an incident, incidents by key, its alerts, its notes, a user), served over TLS with a certificate it mints at startup because the SDK refuses plain HTTP, plus a `/double-control/*` seam that stages an incident whole. Every suite's stack reads it; only `stack` reads the account in `.env`.
  - `test_support/deployment_platform_double/` - the deployment platform held in memory (`InMemoryPlatform`, built from a `PlatformState` seed): a second adapter of `deployment_platform`'s port that no process may run, since a rollback succeeding in memory would have Argus report a mitigation that never happened. Held by the port's suite (`deployment_platform_test/test_port.py`), which asks it and the Argo CD adapter the same questions over one seed.
  - `test_support/flag_provider_double/` - the flag provider held in memory (`InMemoryFlagProvider`, built from a `ProviderState` seed): what the provider holds and what evaluates kept apart, and a history its writes append to. A second adapter of `flag_provider`'s port that no process may run, since a flag switched in memory would have Argus report a mitigation that never happened. Held by the port's suite (`flag_provider_test/test_port.py`), which asks it and both Unleash adapters the same questions over one seed.

## How to run things
Always via `uv run ...` (uses the workspace `.venv`, no manual activation needed) or `uv run python -m nox -s <session>`:

- `uv sync --all-packages` - resolve workspace deps, create/update `.venv` and `uv.lock`. **Always `--all-packages`**: a bare `uv sync` (or `uv run` resolving on the fly) does not reliably install every workspace member's dependencies, and the symptom is spurious import errors out of `nox -s typecheck` that look like a code problem and are not.
- `uv run python -m nox -s schema` - applies the database schema through its job, `python -m apps.schema`, the only way the schema is ever applied. The job runs Alembic's chain (`modules/postgres/src/postgres/migrations/`) to head and drops nothing by default - what a deployment that keeps its data runs. `nox -s schema` passes `--destroy` with `SCHEMA_MAY_BE_DESTROYED=true`, so it drops the schema first: **destructive, and for a development database alone** - the job refuses `--destroy` without that setting, and nothing but a development run sets it. Revision `001` is every table there is; while it is the whole chain it may be edited in place, as though the schema had always said what it now says - the drop is what makes that safe, and a database that keeps its data never sees such an edit. Alters arrive as `002` onwards, and the drop goes when the first one does. `uv run alembic revision -m "..."` writes the next one (root `alembic.ini`; the URL comes from `Settings`, never from that file). No service applies DDL - every service checks the schema is there and refuses to start without it - opening a pool checks, and the write tier asks as it starts. The e2e stack runs the job itself, after postgres and before any service
- `uv run python -m nox -s index` - runs the catch-up loop that keeps the repository index describing what is deployed. Needs postgres and Qdrant up, and reaches GitHub; the first pass on an empty store is the slow one. `--once` is what the e2e stack runs, in the schema job's slot and for the same reason
- `uv run python -m nox -s lint` - ruff check, whole repo
- `uv run python -m nox -s guard_layering` - import-linter over the contracts in the root `pyproject.toml`: no package's modules import one another in a circle (siblings inside a package, at every level - a cycle between two top-level packages is outside it), `core`, `http_applying` and `incident_cost` depend on nothing in this workspace, `incident_record` knows only the kernel and the database, and its repository is imported by nothing that ships outside it, `chat_platform` and `telemetry` only the kernel, `incident_memory` holds records rather than reading the incident record, `postmortem_rendering` says what a postmortem says from values it is handed, `postmortem_writing` never imports `executive_synopsis`, `web_app` serves HTML without installing an agent, the alert and push senders know only the kernel, a process's root in `apps` is the only importer of every adapter (Slack, Argo CD, Unleash, GitHub, Grafana, Prometheus, PagerDuty, Stripe, Frankfurter, BambooHR, Anthropic (`llm_anthropic`), `vector_store_qdrant`, `embedding_fastembed`, and their vendors' settings modules), of the telemetry SDK and of a root, only the deliverer's and the index's roots build the vector store's writing side, no root reaches another, no agent's package knows another's - every package that contract lists (`orchestrator` is absent from that contract, because delegating to all five is what it does), the walk - and the worker's root - writes to no store the fence cannot reach (the contract forbids long-term memory's writing side, the vector store adapter's writing side and the chat platform; the script forbids the `qdrant_client` and `slack_sdk` SDKs through any chain but recall's one read, through `vector_store_qdrant.searching`, and the session then runs the script's own suite in `tests/scripts/`), no module but `vector_store_qdrant` imports `qdrant_client`, none but `embedding_fastembed` imports `fastembed`, and none but `llm_anthropic` imports `anthropic` - only the worker's and the Intent Reader's roots build that adapter, and hand it to every agent as `core.llm.ModelProvider` (the script again, since import-linter sees a third party only with `include_external_packages`, which is global), no shipped module names a vendor outside that vendor's adapter and each process's root - in an identifier or a string, prose aside - but the allowances the script lists, each naming the item that clears it or the decision that keeps it, each root imports only the workspace packages its own extra of `apps` installs (the script, which reads the extras), only the walk makes an admission (the script refuses `core.autonomy.admit` named anywhere that ships outside `orchestrator`, the worker's root, which binds it into the walk, and the kernel - the Mitigator names `Admitted` alone), only a process's root reads the environment (the script refuses `get_settings`, `connect_from_env`, `os.environ` and its kin and any use of a class built on `BaseSettings`, found by following class bases, anywhere that ships outside `apps` - but the kernel's and the database's export lists, where each reader is defined, Alembic's `env.py` and the stack's clock, each reported if it stops reading), the kernel's settings declare no field an adapter's settings declare, the kernel imports and declares no third party but pydantic, pydantic-settings and the OpenTelemetry API (the script, over the graph and over its `pyproject.toml`), every process's root asks for the clock (`core.the_clock`) first thing in `main` - read on first use, so a stack configured by half fails as the process starts - and the kernel is reached through its front doors (`core`, `core.models`, `core.llm`, `core.events`, `core.replay`, `core.anomaly`, `core.budget`, `core.source_scope`, `core.embedding`, `core.vector_store`, `core.stored`, `core.autonomy`, `core.telemetry`) rather than by module path. A broken contract prints the import chain that broke it. The front-door rule is held over `tests/`, `scripts/` and every module's suite by the script itself, and agent independence over each agent's own suite, since import-linter sees only the packages in `root_packages` - which is how one agent's suite came to build a test double out of another agent's code with every contract green
- `uv run python -m nox -s typecheck` - mypy over `modules/` and `tests/` alike; a test is code, and an assertion about a type is worth as much as the type
- `uv run python -m nox -s "test_module(module='<name>')"` - one module's unit and integration tests, isolated deps
- `uv run python -m nox -s test_all` - every module's full test suite
- `uv run python -m nox -s contract` - the free contract tests (Slack, Stripe, Frankfurter, Prometheus); `paid_contract` is the Anthropic one, which spends tokens
- `uv run python -m nox -s grade_fixes` - runs each fix in the recorded corpus against the Target Service's own tests: the patch's test files alone must not pass, then the whole patch must leave `tests/io_shop` green. The only thing that ever finds out whether a proposed fix *works* - Code-Fix runs statically and never learns. Free, keyless and seconds long, so it is on every push; it needs `Argus-Demo-Target-App` checked out beside this repo, and grades each patch side by side in a throwaway worktree of the shop's HEAD, so the shop's own checkout is never written and may be dirty. It lives in `tests/eval/` because it scores the model's answers, and has a session of its own because it is the one eval there that spends nothing - `nox -s eval` ignores it
- `uv run python -m nox -s "e2e_replay(mode='both')"` - the same stack and the same e2e tests, but the worker points at the Anthropic double, so every model answer is replayed from a committed recording. Free, keyless, and what CI runs on every push. Proves the pipeline works; proves nothing about whether the model was right. Parametrized by `CODE_SEARCH`, because each mode is a different stack with a different tool list - and so recordings of its own, stored under that mode's prefix (`grep-feature-flag-toggle`, `both-feature-flag-toggle`). `record(mode=...)` captures a mode's set against the real API. Two things are left uncollected rather than skipped, because the session knows the mode and a skip is a result nobody should learn to read past: under `grep` the index cases, which are about a mechanism that stack does not have, and outside `both` the cases whose claim does not vary by which tool found a file, so recording them per mode would buy three recordings of one assertion
- `uv run python -m nox -s e2e` - brings up docker-compose stack, runs `tests/e2e`, tears down. A subset is run against the real API by naming it - `nox -s e2e -- tests/e2e/<case>.py`. Not `tests/integration`: that suite brings its own postgres up, empties it between cases and stops it at the end, and inside this session it was doing all of that to the stack's own database with the worker still attached. It is free and runs in `sweep` and CI on a project of its own. Reaches the **real** API and spends tokens - run by hand, after a change to the investigation path

**Use `python -m nox`, not the bare `nox` shim** - Windows Smart App Control has blocked the `.exe` stubs in `.venv/Scripts/` before, and going through the interpreter avoids them entirely. It costs nothing when the stubs are fine, which they currently are. When any tool here fails with *"An Application Control policy has blocked this file"* - failing to spawn, or failing to import - see the `smart-app-control-blocks` skill, and read it before changing anything: the fix that looks obvious (`no-binary-package`) is what causes this on packages carrying C, and it has already cost a session once.

**A `|` inside an argument breaks permission matching - keep pipe characters out of arguments entirely.** The allowlist matcher splits the command text on `|` (and `&&`, `||`, `;`) before matching, without respecting quotes: every segment must match a rule on its own, or the whole command falls back to a permission prompt. So any `|` that is *not* a real pipe - a regex alternation, a format string, a column separator, a literal in a message or path - produces junk segments that match nothing, and an otherwise-allowed command stops and waits. This is about the character, not about any particular tool: before running anything, scan the command for `|` and confirm each one is an actual pipe. Where one isn't, use the equivalent that avoids the character - a list or repeated flag instead of an alternation (`-Pattern "a","b"`, `grep -e a -e b`), a character class (`[ab]`), a different delimiter, or a heredoc/script file for literal text. If there is no such alternative, expect the prompt.
  
## Answering - this governs every reply, including mid-task ones

- **The shortest answer that is actually an answer.** Not "brief" - shortest.
  One word where one word does it, one sentence where one sentence does. Two or
  three sentences is the *ceiling* for a normal reply, not the target. If that
  is genuinely not enough, give the short answer first and offer to elaborate -
  do not pre-emptively elaborate.
- **Assume every question carries "shortest possible answer" whether or not it
  says so.** The user should never have to ask for brevity; asking for it means
  the default was already wrong. Having done a lot of work is not a reason to
  write a lot of words about it.
- **When the answer runs long anyway, break it into parts and stop after the
  first.** Let the user say "continue" rather than pre-emptively delivering
  five sections they may not want. Check they follow before moving on.
- **A yes/no question gets `Yes` or `No` as the first word**, and often as the
  whole reply. Add at most one sentence, and only when a bare answer would leave
  the user unable to act.
- **If the question is not answerable as yes/no, say so** - "that isn't a yes/no
  question" - then offer either to answer at length or to have it rephrased.
  Do not quietly answer a different, easier question instead.
- **Asked for a number, a time, or a status: give it.** No formula, no
  derivation, no caveats unless the caveat changes the number.
- **Never restate what was already established** - no recaps of work just
  finished, no summaries of the plan, no repeating the user's own question back.
- Length is earned by the question, not by the size of the work behind it. A
  long investigation still gets a short answer.
- **Long-running jobs run in the background, always** - anything on the scale of
  `e2e`, `e2e_replay`, `contract`, `test_all`, `record` or a docker build. A
  foreground run blocks the whole session until it exits: no status, no reply to
  anything, not even a message from another session. Background it, then report
  *how many of how many* have finished, elapsed time, and expected time to
  complete. The reporting mechanism is a free choice; backgrounding is not. This
  is the one place where saying something unasked is wanted, and it stays one line.
- **Never pipe a backgrounded command through `Select-Object`/`head`/`tail`.**
  They buffer until the process exits, so the output file stays empty and there
  is nothing to report progress *from* - on exactly the long jobs the rule above
  is about. Run it raw, let the file fill live, and filter with `Grep`/`Read`
  when checking it. Same reason a truncated tail hides the real failure: read
  the whole log, narrow afterwards.

## Conventions - follow these without being asked
- **TDD, with `tests/` and `test_support/` off-limits to Claude.** The policy itself lives in `AGENTS.md` (tool-agnostic, applies to any AI coding agent, not just Claude). Mechanically enforced here via `.claude/settings.json` + a PreToolUse hook (`.claude/hooks/block_test_writes.py`) - Claude cannot create or edit files under any `tests/` directory *in this repo*, nor anywhere under `test_support/`: the testkit and every double. `Argus-Demo-Target-App` is outside that rule: it is a fixture, its tests are a regression net written after the code rather than a specification written before it, and Claude writes them directly there. Claude may freely *read* and *run* existing tests (e.g. via `uv run python -m nox -s test_module`). For the exact workflow to propose a new test, see the `tdd-new-behavior` skill. **Propose the entire file, never a fragment** - the human pastes it whole, and a set of "add this after line 40" instructions is how a test file quietly ends up not saying what either party thinks it says. Targeted edits only when tiny and precisely located.
- **Commit messages are a single line.** No body, no bullet list, no trailers. Draft the exact line, get approval on that line, then commit - see the `git-commit-approval` skill. Argus and `Argus-Demo-Target-App` are separate repos and commit separately.
- **Type hints on every function signature** (params and return type), matching mypy's expectations under `nox -s typecheck`. `-> None` for no return, not omitted.
- **Docstrings**: every nox session function gets a two-part docstring (what it registers as / how to invoke it, then what it actually does) - see the `nox-session-style` skill. Match this style for other non-trivial functions too (agents, tools, orchestrator FSM).
- **Ruff rule sets in play**: E, F, I, UP, B, SIM (see root `pyproject.toml`). Don't disable a rule inline without flagging it - ask first.
- **No trailing comma before a closing bracket.** `)`, `}` and `]` follow the last item directly, in calls, literals and signatures alike. The one exception is a wrapped `import`, where ruff's import rule requires one and wins.
- **No magic strings from an external protocol - name them, and type them `Final`.** A vendor's wire vocabulary (Anthropic's `"tool_use"`, `"end_turn"`, `"text"`, `"thinking"`, `"assistant"`) gets a named constant at the top of the module that reads it. `Final` is not cosmetic: the SDK types these fields as `Literal`s, so a bare `str` fails mypy on the way in and, worse, stops it narrowing a discriminated union on the way out - every branch of `block.type == ...` then errors. Name the constant for the *field*, not the spelling: `TOOL_USE_TYPE` and `TOOL_USE_STOP_REASON` are the same string and different things. See the `wire-vocabulary-constants` skill.
- **pytest markers**: tag every test with exactly one of `unit`, `component`, `integration`, `e2e`, `contract`, `eval` (declared in root `pyproject.toml`, each with a one-line definition of what it means). Don't add a new marker without updating that list. `component` is the one most often mislabelled: one module entire, through its own front door, with only the infrastructure it cannot fake brought up around it - which is `integration` only if it spans two modules.
- **`e2e`-marked tests only live in root `tests/e2e/`, never inside a module's own `modules/*/tests/`** (enforced via `nox -s guard_e2e_boundary` / pre-commit). See the `e2e-test-placement` skill for which directory and marker any given test belongs in.
- **One test file per source module, named after it** - `writing.py` is covered by `test_writing.py`. A collaborator a module *delegates to* gets an injection seam, so the caller's test mocks it rather than re-testing it through a finished result - not one it merely computes with (`the_response_priced` calls `responder_cost` directly, and asserts real figures); the whole package through its front door, every internal collaborator real, is a `component` test in `<module>_test/component/`. A test's `when` calls the thing under test directly - builders build values, never wrap the call. See the `unit-and-component-boundaries` skill.
- **A module's tests live in `modules/<module>/tests/<module>_test/`**, with `__init__.py` from that package down and none in `tests/` itself. mypy checks everything in one process, so two `conftest`, `framework` or `tests` packages across modules collide on import - and naming the package `<module>` instead of `<module>_test` shadows the real package. Sub-packages (`framework/`, one per subject area) sit inside it. Within a suite, import by the package's own name (`from <module>_test.framework.builders import ...`), never by a path through the repo (`modules.<module>.tests....`): that spelling gives one file two module names and mypy refuses it.
- **Root `tests/` is a package tree** - `__init__.py` in `tests/` and every directory under it - and its suites import each other as `tests.framework.assertions`, `tests.e2e.framework.argus`. Without the markers the same file is reachable under two names, since those imports make the repo root a package base while a directory with no `__init__.py` is a base of its own.
- **A package's `__init__.py` is an export list, never code.** Docstring, imports and `__all__` - no `def`, no `class`, no constant, no type alias. The entry point is not an exception: `write_postmortem` lives in `postmortem_writing/writing.py` and is re-exported from there. See the `package-init-is-exports-only` skill.
- **Module boundaries**: don't reach into another module's `src/` directly - depend on it as a workspace package (`{ workspace = true }`) and import its public API only. If two agent modules need to share logic, that logic belongs in `modules/core/`, not copy-pasted (or exposed via API). For the kernel this is enforced rather than asked: `core` is reached through its front doors, so `from core.models import Alert`, never `from core.models.alert import Alert` - and a kernel module that is not a front door is internal by default, so making a new one public is a line somebody writes in the contract's `ignore_imports`.
- **A type two modules both name is a contract, and a contract lives in `core.models`.** `PostmortemDocument` and `PublishedRates` are there rather than in the agent and the source that produce them, because the repository that persists one and the walk that carries it name them too - and a contract kept inside one of the parties is one the other installs an agent to read. The layering this rests on is enforced, not described: `nox -s guard_layering` fails the build if `core`, `incident_record` or `web_app` gains a dependency it may not have.
- **Reversible vs. irreversible actions** (see spec §13): code that touches the sandbox's flag/deploy APIs must be tagged/logged as reversible mitigation. Anything resembling "merge a PR" or an infra apply must never be autonomous - always require explicit human approval in the code path, no exceptions, even in test/demo code.
- **No duplicate tool invocations across pre-commit and nox.** Before adding a new pre-commit hook, see the `pre-commit-hook-style` skill.
- **Private means private - across every boundary, tests included.** A leading `_` marks a name as belonging to its own module. Nothing outside that module may import or call it: not production code, not tests, not "just for testing". Python not enforcing this is not permission to ignore it. If a test needs to reach a `_name`, that is the design telling you the thing under test has no public seam - extract it into a module whose public API *is* the unit, and test that. Never widen a test's reach instead of widening the code's API.
- **Test variable naming: `some_` for arbitrary values, `dont_care_` for required-but-irrelevant ones, `a_`/`an_` for builders, no prefix when the value itself matters.** See the `test-naming-style` skill.
- **Tests are written as `Scenario().given(...).when(...).then(...)`** - the three phases stay visible even in a unit test whose "given" is one builder call. Assert through `all_of(...)` rather than a run of bare `assert`s: a run stops at the first failure, so a translation that lost two fields reports one. Assertions raise `AssertionError` with their own message saying what was expected and what came back, and live as `_`-prefixed helpers in the test file when they are specific to it - only genuinely reusable ones belong in `argus_testkit`, which Claude may not edit.
- **Repository method naming: bare `get()` only for primary-key lookups.** Anything relational - a lookup by foreign key, "the latest X for this Y" - gets a descriptive `get_*` name saying what it looks up by. `get()` with no qualifier is a promise that the argument is the identity.
- **`docs/spec-and-architecture.md` is a specification, not a changelog** - it describes the design as though it were always the intent. See the `spec-doc-style` skill before editing it.
- **Argus's own code is held to a high bar; `Argus-Demo-Target-App` is a fixture and is not.** Shortcuts are fine in the demo app and expected. A shortcut landing in Argus itself gets raised before it lands, not after.
- **A contract test needs a genuinely external party** - one that can change out from under you. `tests/contract/` is contract testing in Fowler's sense precisely because `anthropic_double` stands in for the Anthropic API: the tests check that a call against the double returns what a call to the real service would. **Argus's own components are not external to each other**, however many module boundaries sit between them - a cross-module seam changes only when this repo changes it, and a test asserting one module still matches another belongs in that module's own suite, not here.
- **A double knows its vendor's behaviour, never a scenario's contents.** Anything particular a standalone double has to answer with - a commit sha, a message, a canned response - is staged by the case that needs it, through a `POST /double-control/*` endpoint, and cleared by `reset()`. The double names nothing and reads the same whichever scenario is running. See the `double-seeding-style` skill.
- **Test doubles: `unittest.mock` (`create_autospec`, `Mock(spec=...)`) is fine, `patch()` is not.** Dependencies get injected via a default-argument parameter (or, for 2+ related collaborators reused across calls, a constructor) - never via monkeypatching a module-level import. See the `test-mocking-style` skill for the full reasoning and known `create_autospec` gotchas before writing test doubles.

## Things NOT to do
- New modules are welcome and expected as the system grows - this rule is only about *how* to add one. Don't hardcode a module into `noxfile.py`; it's auto-discovered from `modules/*/pyproject.toml`, so a module missing from `nox --list` needs its `pyproject.toml` written, not `noxfile.py` edited. See the `new-module` skill. The one list a new module *does* have to join is `[tool.importlinter] root_packages` - import-linter takes no wildcard there, and a package it cannot see is a package no contract can be broken by. `nox -s guard_layering` fails and names the module if you forget; which layer it belongs to is yours to decide, which is why nothing adds it for you.
- Don't rename `pyproject.toml`, `uv.lock`, or `conftest.py` - these filenames are fixed by tooling convention, not configurable.
- Don't put per-tool config in separate files (`ruff.toml`, `pytest.ini`, etc.) unless asked - everything currently lives in the root `pyproject.toml` deliberately, as one scannable source of truth for the whole workspace.
