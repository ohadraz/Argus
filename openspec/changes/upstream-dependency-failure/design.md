## Context

The Target Service's scenarios all stage a condition inside the deployment: a
flag's value, a deploy record, a process's own accumulation. Each is something
Argus can address, and the whole walk is built around addressing it. A
propagation failure is the opposite shape - the condition belongs to somebody
else, and the correct response is to name it and stop.

Two pieces of machinery already exist and are not being rebuilt here. The
Investigator determines a `FailureMode` from evidence, and a mode with no
strategy in `DEFAULT_STRATEGIES` already produces no action, is refused at the
gate, and ends the incident escalated with a postmortem. What is missing is a
scenario that produces the evidence, a mode to name it, and a refusal that says
which of the two silences it is.

The demo's metrics are generated by rendering real account pages in-process -
`_SAMPLE_SIZE` of them per minute, across a 90-minute window. That constrains
how the dependency can be modelled: whatever the page calls must be answerable
without a network round trip per render.

## Goals / Non-Goals

**Goals:**

- An incident that is diagnosed confidently and escalated because no mitigation
  in Argus's closed set answers it - the first of its kind.
- Evidence that distinguishes an upstream failure from an internal one, in the
  channels Argus already reads.
- A refusal a human can tell apart from "nobody could identify an action".
- A scenario no Argus action ends, so grading stays telemetry-driven.

**Non-Goals:**

- Retry, circuit-breaking or fallback behaviour in the shop. The shop's code is
  not at fault in this scenario and nothing here should imply a code fix.
- A dependency-health retrieval tool, or per-dependency metric fields. The logs
  already carry what distinguishes this, and a new read channel is a second
  change wearing this one's clothes.
- Any change to how escalation itself works - the route, the status and the
  postmortem are the ones that already run.

## Decisions

### The dependency is on the page-render path, called through a seam

`io_shop` gains a payment-provider client, called while rendering the account
page to show the shopper's stored card. It is a seam, not a socket: the
generator renders two hundred pages a minute over a ninety-minute window, and a
real HTTP call per render would be tens of thousands of requests per `/metrics`
read. The client is handed what the provider is currently doing, the same way
the page is handed the flag decision rather than evaluating it.

*Alternative considered*: a checkout path with a real HTTP hop to a stand-in
endpoint. Rejected on cost - the honest part of this scenario is what the logs
say and what the metrics do, and neither is improved by a socket.

### The shop's code stays correct

The provider raises, the request boundary catches it and records the failure
with the raising line, exactly as it does today. No retry, no fallback, no
degradation path - because adding one would make this an incident about the
shop's resilience, and this is an incident about somebody else's outage.

### Latency moves with the error rate

An upstream failure shows up as both: requests wait for the provider before
failing. The generator applies a wait to the minute's latency while the
provider is failing, which puts the scenario's signature - errors *and* latency
up, memory flat, nothing changed - in the metrics the Investigator reads first.

*Alternative considered*: errors only, latency flat. Rejected: that is the
feature-flag signature, and two scenarios that read identically at the metrics
level make the mode determination a coin toss.

### A refusal of its own

`Refusal.NOTHING_ANSWERS_THIS_MODE`, given when the hypothesis names a mode and
no member of the closed set answers it. `NO_MITIGATION_PROPOSED` stays what it
is: an action nobody could identify, which is a gap in the evidence.

The gate asks `agent_mitigation` which of the two it is - policy answers what
policy knows - rather than looking up the strategies mapping itself. The gate's
job is to refuse, not to hold a second copy of what Argus can do.

### The scenario is cleared only by the demo's own control

No flag, no restart, no deploy record ends it. It stops when the scenario is
reset, which is the operator's doing and not Argus's - so an agent that
reverted something to see what happened is graded by telemetry that carries on
failing.

## Risks / Trade-offs

- **The model calls it a bad deployment instead** → the change-events channel is
  empty for this window and the logs name a third-party host and an HTTP status
  on every failure line. If it still misreads, the eval suite is where that is
  caught rather than the e2e.
- **Two scenarios now raise latency** (this and the leak) → they are told apart
  by memory, which is flat here and climbing there, and by the logs.
- **Recordings cost tokens** → the e2e case needs a recording per `CODE_SEARCH`
  mode, captured deliberately with `nox -s "record(mode=...)"`, not as a side
  effect of a green run.
- **A refusal value is persisted** → `ActionRefused` carries it, so the
  vocabulary is one a stored row can hold; adding a value is additive and no
  existing row changes meaning.
